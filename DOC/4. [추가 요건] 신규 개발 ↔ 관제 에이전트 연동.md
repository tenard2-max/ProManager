# [추가 요건] 신규 개발 ↔ 관제 에이전트 연동

작성 대상: 이후 모든 신규 개발(제품/모듈)을 수행하는 Cursor IDE · 그록 봇 · 발주자  
기준 문서: `3. [개발 요건서] 에이전트 감시 관제 시스템` · 관제 구현체: `monitor_agent/`  
작성일: 2026-11-13 · 버전: v1.0

---

## 0. 목적

신규 개발은 **코드만 작성하고 끝나지 않는다.**  
반드시 로컬 관제 에이전트(`http://127.0.0.1:18765`)에 요건·진행·QA를 보고하고, 발주자 명령을 받아 작업한다.

본 문서는 기존 관제 요건서에 **붙이는 추가 요구사항**이다. 충돌 시 본 문서의 “연동 의무”가 신규 개발 작업 절차를 우선한다.

---

## 1. 적용 범위

| 구분 | 내용 |
|------|------|
| 포함 | 신규/변경 개발 착수, 구현 중 보고, QA 제출, 발주자 재작업·승인 대응 |
| 제외 | 관제 서버 자체 기능 변경(별도 관제 요건서), 제품 제품 제품의 제품 알고리즘 내부 |

**의무 주체**

- Cursor IDE: 구현 + `SPEC_RESET` / `STATUS_UPDATE` / `HEARTBEAT` / 명령 ACK
- 그록 봇: 독립 QA + `QA_RESULT` / `HEARTBEAT` / 명령 ACK
- 발주자: 관제 UI에서만 지시·최종 승인 (progress 직접 수정 금지)

---

## 2. 착수 전 필수 조건

신규 개발을 시작하기 전에 아래를 **모두** 만족해야 한다.

1. 관제 서버가 실행 중일 것 (`monitor_agent/run_server.bat` 또는 `python -m app.main`).
2. 브라우저에서 `http://127.0.0.1:18765/` 대시보드가 보일 것.
3. 해당 신규 개발의 **개발 요건서 MD**가 존재할 것.
4. 요건서의 모든 구현 항목이 `REQ_XXX` 형식의 **요건 INI**로 매핑되어 있을 것.
5. Cursor IDE가 `SPEC_RESET`으로 관제에 요건을 등록하고, UI에 항목이 표시된 것을 확인할 것.

착수 체크가 하나라도 실패하면 **코드 작성에 들어가지 않는다.**

---

## 3. 요건 INI 작성 규칙 (신규 개발용)

신규 개발 요건서는 반드시 관제 `spec.ini` 스키마로 옮긴다.

### 3.1 필수 구조

```ini
[META]
project_name = {신규 프로젝트명}
spec_version = {정수, 요건 변경 시 +1}
spec_source = {개발 요건서 MD 경로}
submitted_by = cursor
submitted_at = {ISO 8601}

[REQ_001]
title = {한 줄 제목}
category = {모듈/영역명}
priority = HIGH|MEDIUM|LOW
spec_ref = {요건서 절 번호}
acceptance_criteria = {검증 가능한 완료 조건 1줄}
target_files = {예상 산출 파일 경로, 쉼표 구분}
```

### 3.2 추가 작성 규칙

1. 섹션 ID는 `REQ_001`부터 연속·고유. (`TASK_01` 등 구 형식 금지)
2. `acceptance_criteria`가 비어 있으면 등록 거부된다. 모호한 문구(“잘 동작”, “완료”) 금지.
3. 이미 구현된 항목도 초기에는 `TODO` 또는 보고 후 `IN_REVIEW` + `progress ≤ 60`으로 올린다. **초기값 61 이상 금지.**
4. 요건이 바뀌면 `spec_version`을 올리고 다시 `SPEC_RESET`한다. Cursor가 `spec.ini`를 임의로 조용히 덮어쓰지 말고, 반드시 메시지를 통해 재설정한다.

## 4. 개발 중 Cursor IDE 연동 의무

### 4.1 통신 채널

- Base URL: `http://127.0.0.1:18765`
- 송신: `POST /api/messages`
- 명령 수신: `GET /api/messages/outbox?agent=cursor` (권장 주기 5초 이내)
- 참고 클라이언트: `monitor_agent/tools/agent_client.py`

### 4.2 메시지 의무

| 시점 | type | 내용 |
|------|------|------|
| 착수/요건 변경 | `SPEC_RESET` | `payload.spec_ini`에 요건 INI 전문 |
| 항목 작업 시작 | `STATUS_UPDATE` | `status=IN_PROGRESS`, `progress` 0~60 |
| 자가 검증 완료 | `STATUS_UPDATE` | `status=IN_REVIEW`, `progress=60`, `dev_note`에 근거 |
| 상시 | `HEARTBEAT` | 30초 주기. 90초 끊기면 UI OFFLINE |
| 명령 수신 후 | `ACK` | outbox 명령의 `msg_id`를 `payload.ack_for`로 응답 |

### 4.3 진행률 권한 (위반 시 REJECT)

- Cursor는 `progress`를 **0~60만** 설정할 수 있다. 61 이상은 거부된다.
- Cursor는 `status=VERIFIED`를 직접 설정할 수 없다.
- Cursor는 `qa_status`, `qa_score`, `qa_rework_count`를 쓰지 않는다.
- `state_version` 낙관적 잠금을 쓸 경우, 불일치 시 최신 상태를 다시 읽고 재시도한다.

### 4.4 작업 선택 규칙

1. 작업 전 관제 상태(또는 outbox 명령)를 확인한다.
2. 우선순위: 발주자 `COMMAND`(수정 지시·추가 검증) > `REWORK_REQUESTED` > `TODO` > `IN_PROGRESS`.
3. `VERIFIED` 항목은 발주자 지시 없이 재수정하지 않는다.
4. 한 번에 보고하는 항목과 실제 수정 파일이 `target_files`와 어긋나면 `dev_note`에 사유를 남긴다.

## 5. 그록 봇 QA 연동 의무

### 5.1 검증 대상

- 기본 대상: `status=IN_REVIEW` 이고 `qa_status=PENDING`인 항목
- 발주자가 `qa_reeval` / `extra_verify` 명령을 내린 항목은 최우선

### 5.2 보고 규칙

| 결과 | QA_RESULT payload | 관제 측 효과 |
|------|-------------------|--------------|
| 합격 | `qa_status=PASSED`, `qa_score` 0~100 | progress = `80 + round(qa_score×0.2)` |
| 불합격 | `qa_status=FAILED_REWORK`, `qa_diff_note`에 결함 | progress=60, `REWORK_REQUESTED`, 반려 횟수 +1 |

### 5.3 금지

- `progress`를 61~79로 저장하는 행위
- Cursor 구현 파일을 그록이 직접 수정하는 행위(결함은 note로만 전달)
- HEARTBEAT 생략(30초 주기 동일)

## 6. 발주자(관제 UI) 연동 요건

발주자는 관제 UI만 사용한다.

| 명령 | 효과 | 대상 에이전트 |
|------|------|----------------|
| 추가 검증 요청 | `IN_REVIEW` + `qa_status=PENDING`, 조건은 `qa_diff_note` | 그록(검증) / 필요 시 Cursor |
| 수정 지시 | `REWORK_REQUESTED` + 지시문 기록 | Cursor |
| QA 재평가 요청 | `qa_status=PENDING` | 그록 |
| 최종 승인 | `qa_status=PASSED`인 항목만 `VERIFIED` | (상태 확정) |

최종 승인 전에는 어떤 항목도 “개발 완료”로 문서·보고하지 않는다.

## 7. 신규 개발 표준 워크플로

```text
[1] 요건서 MD 작성
      ↓
[2] 요건 → spec.ini(REQ_*) 매핑
      ↓
[3] 관제 서버 기동 + UI 확인
      ↓
[4] Cursor: SPEC_RESET → UI에 항목 표시 확인
      ↓
[5] Cursor: 구현 → STATUS_UPDATE(≤60, IN_REVIEW)
      ↓
[6] 그록: QA_RESULT (PASSED | FAILED_REWORK)
      ↓
[7] 실패 시 Cursor 재작업 루프 / 성공 시 발주자 최종 승인
      ↓
[8] VERIFIED 비율·감시 지표로 종료 판정
```

### 7.1 단계별 DoD (신규 개발 단위)

1. UI에 해당 `REQ_*`가 모두 보인다.
2. Cursor ONLINE, 그록 ONLINE이 작업 구간에 유지된다.
3. 자가 완료 보고는 모두 `progress=60` + `IN_REVIEW`이다.
4. QA 없이 `VERIFIED`가 된 항목이 0건이다.
5. 발주자 명령에 대해 Cursor/그록이 ACK를 남긴다.
6. 이력 로그(`events.jsonl`)에 SPEC_RESET·STATUS_UPDATE·QA_RESULT가 남는다.

## 8. Cursor 프로젝트 규칙 (신규 개발 저장소에 추가)

신규 개발 저장소 루트에 아래 규칙을 넣는다. (예: `.cursorrules` 또는 Cursor Rules)

```text
1. 모든 구현 작업 전 관제 에이전트(http://127.0.0.1:18765) 연결을 확인한다.
2. 요건 항목은 monitor_agent 스키마의 REQ_* / project_status 상태를 따른다.
3. progress는 60을 초과해 보고하지 않는다.
4. REWORK_REQUESTED 및 발주자 COMMAND 대상 항목을 최우선으로 처리한다.
5. 작업 종료 시 STATUS_UPDATE로 dev_note와 상태를 보고하고, outbox 명령에 ACK한다.
6. 관제 미기동 상태에서 대규모 구현을 진행하지 않는다.
```

---

## 9. 권장 디렉터리 연계

신규 개발 프로젝트와 관제를 같은 워크스페이스에서 쓸 때의 권장 배치:

```text
ProjManager/
  DOC/                          # 요건서·본 추가 요건
  monitor_agent/                # 관제 서버·UI
  {신규프로젝트}/               # 실제 제품 코드
    .cursorrules                # 8장 규칙
    docs/requirements.md        # 해당 제품 요건서
```

- 관제 데이터 파일은 `monitor_agent/data/`에 둔다.
- 신규 프로젝트가 `project_status.ini`를 자체 루트에 또 만들어 **이중 원본**이 되지 않게 한다.  
  **상태의 단일 원본(Single Source of Truth)은 관제 에이전트다.**

## 10. 수용 기준 (본 추가 요건 DoD)

1. 신규 개발 착수 시 `SPEC_RESET` 없이 구현만 진행하면 절차 위반으로 본다.
2. Cursor가 progress 61 이상을 보내면 REJECT를 받고, 상태 파일이 변하지 않는다.
3. 그록 `FAILED_REWORK` 1회에 `qa_rework_count`가 정확히 1 증가한다.
4. 발주자 최종 승인은 `qa_status=PASSED` 항목에만 가능하다.
5. HEARTBEAT 중단 후 90초 이내 UI에 OFFLINE이 표시된다.
6. 신규 개발 종료 보고에는 관제 지표(요건 충족률, 평균 반려, 첫 검증 합격률)를 첨부한다.
