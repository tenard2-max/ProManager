# &#91;개발 요건서\] 에이전트 감시 관제 시스템 (Cursor IDE · 그록 봇 모니터링)

작성 대상: 구현 에이전트(Cursor IDE 연동 감시 서버 + UI) · 발주자: {이름/팀} · 작성일: {YYYY-MM-DD} · 버전: v1.0

## 0. 개요

**목적** 본 시스템은 개발 요건서를 기준으로 Cursor IDE(생산 라인)와 그록 봇(독립 QA)이 자기 일을 얼마나 정확히 수행하는지 실시간으로 감시하는 관제 에이전트다. 발주자는 관제 UI만 보고 Cursor IDE와 그록 봇에 지시를 내린다. 두 에이전트는 이 관제 에이전트의 지시를 받아 움직인다.

**핵심 흐름**

1. Cursor IDE가 개발 요건서를 입수하면 관제 에이전트에 메시지로 요건 INI 재설정을 요청한다.
2. 관제 에이전트는 요건 INI를 검증하고 상태 INI를 생성 또는 갱신한다.
3. 관제 에이전트는 5초 주기로 상태 INI를 감시하고, 변경 사항을 UI에 반영한다.
4. 발주자는 UI에서 상태를 확인하고 명령을 입력한다. 명령은 관제 에이전트를 거쳐 Cursor IDE 또는 그록 봇에 전달된다.
5. 그록 봇은 QA 대상 항목을 검증하고 결과를 메시지로 보고한다. 결과는 상태 INI에 기록되고 UI에 표시된다.

**용어**

- 관제 에이전트: 본 요건서가 정의하는 감시 서버와 UI 전체를 말한다.
- Cursor IDE: 구현 주체. 요건 항목을 코드로 구현하고 자가 보고한다.
- 그록 봇: 독립 QA 주체. 구현 결과를 검증하고 점수와 결함을 보고한다.
- 요건 INI(spec.ini): 개발 요건서 항목을 INI 형식으로 옮긴 원본 명세. 사람이 정의하며 Cursor IDE는 이를 재설정 요청할 수 있으나 임의 수정할 수 없다.
- 상태 INI(project\_status.ini): 각 항목의 진행 상태, 완성도, QA 결과를 담는 파일. 관제 에이전트가 단독으로 검증하고, 쓰기 권한은 6장에 따른다.
- 명령(Command): 발주자가 UI에서 입력한 지시. 대상 에이전트와 항목 ID를 지정한다.

**범위**

- 포함: 요건 INI 수신과 검증, 상태 INI 관리, 5초 감시 루프, 메시지 통신, 관제 UI, 명령 전달, 감시 지표 산출, 이력 로그.
- 제외: Cursor IDE 내부 코드 생성 로직, 그록 봇의 검증 알고리즘 자체, 실제 제품(EMV, XFS) 기능의 구현. 본 시스템은 이들을 감시만 한다.

## 1. 시스템 구성

```
[Cursor IDE] --(SPEC_RESET / STATUS_UPDATE 메시지)--> [관제 에이전트 서버]
[그록 봇]    --(QA_RESULT 메시지)-------------------> [관제 에이전트 서버]
[관제 에이전트 서버] --(COMMAND 메시지)-------------> [Cursor IDE / 그록 봇]
[관제 에이전트 서버] <--(5초 감시 루프)--> [spec.ini / project_status.ini]
[관제 에이전트 서버] --(WebSocket 또는 폴링 API)--> [관제 UI (브라우저)]
```

**구성 요소**

- 메시지 수신기: 에이전트들이 보내는 메시지를 받아 검증 후 큐에 넣는다.
- 상태 저장소: 상태 INI 파일과 이력 로그를 관리한다. 모든 쓰기는 이 모듈을 거친다.
- 감시 루프: 5초마다 파일 해시와 스키마를 검사하고 변경을 감지한다.
- 명령 전달기: 발주자 명령을 대상 에이전트의 수신 큐에 넣고 확인 응답을 추적한다.
- 관제 UI: 상태를 시각화하고 명령을 입력받는다.
- 지표 산출기: 6장 감시 지표를 계산한다.

**배치 원칙**

- 관제 에이전트와 UI는 로컬 PC에서 실행하며 127.0.0.1에만 바인딩한다.
- 외부 네트워크 전송은 하지 않는다.

## 2. 데이터 규격

### 2.1 요건 INI (spec.ini)

요건 항목 하나가 INI 섹션 하나에 대응한다. 섹션 이름은 `[REQ_001]` 형식이며 고유해야 한다.

```
[META]
project_name = EMV_XFS_Simulator
spec_version = 1
spec_source = {개발 요건서 문서 경로 또는 링크}
submitted_by = cursor
submitted_at = 2026-11-13T10:00:00+09:00

[REQ_001]
title = BER-TLV 파서 및 APDU 상태 머신 구현
category = Core_Engine
priority = HIGH
spec_ref = {요건서 절 번호}
acceptance_criteria = {검증 가능한 조건을 한 줄로 기술}
target_files = src/tlv_parser.cpp, include/tlv_parser.h
```

**필수 키**

- META: project\_name, spec\_version, submitted\_by, submitted\_at
- REQ 섹션: title, category, priority, spec\_ref, acceptance\_criteria, target\_files

**검증 규칙**

1. 섹션 ID는 중복될 수 없다.
2. 필수 키가 하나라도 없으면 해당 섹션은 거부하고 오류로 기록한다.
3. priority는 HIGH, MEDIUM, LOW 중 하나여야 한다.
4. acceptance\_criteria가 비어 있으면 거부한다. 검증 기준 없이 완성 판정을 할 수 없기 때문이다.
5. 요건 INI가 재설정되면 기존 상태 INI의 항목 ID와 대조해 추가, 삭제, 변경된 항목을 이력에 기록한다.

### 2.2 상태 INI (project\_status.ini)

```
[META]
project_name = EMV_XFS_Simulator
total_tasks = {N}
overall_progress = {자동 계산}
state_version = {정수, 쓰기마다 증가}
last_updated_by = {agent 이름}
last_updated_at = {ISO 8601}

[REQ_001]
title = BER-TLV 파서 및 APDU 상태 머신 구현
category = Core_Engine
status = IN_REVIEW
progress = 60
qa_status = PENDING
qa_score = 0
qa_rework_count = 0
dev_note = 1차 모듈 구현 및 컴파일 완료
qa_diff_note =
last_updated_by = cursor
last_updated_at = 2026-11-13T10:05:00+09:00
```

**필드 정의**

- status: TODO, IN\_PROGRESS, IN\_REVIEW, REWORK\_REQUESTED, VERIFIED 중 하나
- progress: 0\~100 정수
- qa\_status: PENDING, PASSED, FAILED\_REWORK 중 하나
- qa\_score: 0\~100 정수, 그록 봇만 기록
- qa\_rework\_count: 0 이상 정수, 반려될 때마다 1 증가
- qa\_diff\_note: 그록 봇의 결함 기록 또는 발주자의 추가 검증 조건

## 3. 메시지 통신 프로토콜

모든 에이전트 간 통신은 아래 메시지 봉투를 사용한다. 봉투 형식은 INI 라인 단위가 아니라 JSON 한 줄 객체로 전송하며, 전송 채널은 로컬 소켓 또는 로컬 HTTP 중 하나로 확정한다(7장 미확정 사항 참조).

**메시지 봉투 필드**

- msg\_id: 고유 식별자. 중복 수신 방지에 사용한다.
- type: 메시지 유형 (아래 표)
- from: cursor, grok, user 중 하나
- to: agent 또는 cursor 또는 grok
- ts: 송신 시각 (ISO 8601)
- schema\_version: 프로토콜 버전
- payload: 유형별 내용

**메시지 유형**

| type | 송신 | 수신 | 설명 |
| --- | --- | --- | --- |
| SPEC\_RESET | cursor | agent | 요건 INI 재설정 요청 |
| STATUS\_UPDATE | cursor | agent | 항목 진행 상태 및 dev\_note 갱신 |
| QA\_RESULT | grok | agent | 항목별 qa\_score, qa\_status, qa\_diff\_note |
| COMMAND | user (UI 경유) | cursor 또는 grok | 발주자 지시 전달 |
| ACK | 수신자 | 송신자 | 메시지 수신 및 처리 완료 응답 |
| HEARTBEAT | cursor, grok | agent | 연결 생존 확인. 30초 주기 |

**통신 규칙**

1. 모든 메시지는 수신 후 ACK로 응답해야 한다. 10초 내 ACK가 없으면 재전송하며 최대 3회까지 시도한다.
2. 같은 msg\_id를 다시 받으면 처리하지 않고 ACK만 다시 보낸다(멱등 처리).
3. HEARTBEAT가 90초 동안 없으면 해당 에이전트를 OFFLINE으로 표시한다.
4. 스키마 검증에 실패한 메시지는 버리고 오류 이력에 기록한다. 송신자에게는 REJECT 응답을 보낸다.

**예시 (SPEC\_RESET)**

```
{ msg_id: ..., type: SPEC_RESET, from: cursor, to: agent, payload: { spec_ini: <요건 INI 전문> } }
```

## 4. 5초 감시 루프

**주기**

- 상태 INI와 요건 INI를 5초 주기로 검사한다. 허용 오차는 ±1초다.
- 주기 검사는 파일 해시 비교로 먼저 변경을 감지한다. 해시가 같으면 파싱하지 않는다.

**루프 단계**

1. 두 파일의 해시를 계산하고 직전 값과 비교한다.
2. 변경이 있으면 INI를 파싱하고 스키마를 검증한다.
3. 검증을 통과하면 새 스냅샷을 마지막 정상 스냅샷으로 저장한다.
4. 변경된 필드를 계산해 이력에 기록한다.
5. 지표를 재계산하고 UI 구독자에게 갱신을 보낸다.
6. 모든 에이전트의 HEARTBEAT 상태를 갱신한다.

**장애 처리**

- INI 파싱 실패: 마지막 정상 스냅샷을 유지하고 UI에 경고를 띄운다. 파싱 실패한 내용은 쓰기 기준으로 사용하지 않는다.
- 파일 잠금 충돌: 최대 3회 재시도하고, 실패하면 이력에 기록한다.
- 5초 주기 초과(검사 지연): 지연 시간을 이력과 UI에 표시한다.

**쓰기 충돌 방지**

- 상태 INI에는 state\_version을 둔다. 쓰기 요청이 들어올 때 기대 버전이 현재 버전과 다르면 거부하고 송신자에게 재시도를 요구한다.

## 5. 진행률 권한 규칙

진행률은 누가 어느 구간을 설정할 수 있는지 명확해야 한다. 이 규칙은 Cursor IDE와 그록 봇이 서로의 영역을 침범하지 않도록 하고, 발주자가 자기 보고와 독립 검증 결과의 차이를 볼 수 있게 한다.

| 구간 | 설정 주체 | 조건 | 상태 |
| --- | --- | --- | --- |
| 0 \~ 60 | Cursor IDE | 구현과 자가 검증 완료 | IN\_PROGRESS, IN\_REVIEW |
| 60 고정 | Cursor IDE | 구현 완료 보고. 60을 넘기는 값은 거부됨 | IN\_REVIEW |
| QA 판정 | 그록 봇 | 60 항목에 대해 검증 수행 | qa\_status 갱신 |
| 80 \~ 100 | 그록 봇 | qa\_status = PASSED일 때만 가능. 값은 qa\_score에 따라 산정 | VERIFIED |
| 재수정 | 그록 봇 | 결함 발견 시 progress를 60으로 되돌리고 반려 횟수 증가 | REWORK\_REQUESTED |

**산정식 (ASSUMPTION-1, 확정 전까지 임시 적용)** QA PASSED 시 progress = 80 + qa\_score × 0.2 (반올림) 예: qa\_score 90 → progress 98

**주의: 61\~79 구간** 이 구간은 값으로 사용하지 않는다. QA 진행 중 표시용으로만 쓴다(QUESTION-1 참조).

**발주자 권한**

- 발주자는 progress 값을 직접 수정할 수 없다.
- 발주자는 상태를 VERIFIED로 확정하는 최종 승인 버튼만 가진다. 이 버튼은 qa\_status = PASSED인 항목에만 활성화된다.

## 6. 관제 UI 요건

**기술 기준**

- 직접 CSS를 작성하지 않는다. Tailwind와 검증된 오픈소스 컴포넌트(MIT 또는 Apache 2.0)만 사용한다.
- 다크 테마를 기본으로 한다.
- 화면 갱신은 5초 주기에 맞춘다. 마지막 동기화 시각과 다음 갱신까지 남은 시간을 상단에 표시한다.

**화면 구성**

1. 전체 대시보드
   - 전체 평균 완성도 게이지
   - 카테고리별 진행률 바. 각 바는 Cursor 구간(0\~60)과 QA 구간(61\~100)을 색으로 구분한다.
   - 상태별 항목 수 요약 (TODO, IN\_PROGRESS, IN\_REVIEW, REWORK\_REQUESTED, VERIFIED)
   - 에이전트 연결 상태 (Cursor IDE, 그록 봇: ONLINE 또는 OFFLINE)
2. 항목 목록
   - 열: ID, 제목, 카테고리, 상태 뱃지, progress, qa\_status, qa\_score, 반려 횟수, 최종 갱신 시각
   - 필터: 상태, 카테고리, qa\_status, 반려 횟수 1 이상
   - 정렬: 반려 횟수, progress, 최종 갱신 시각
3. 항목 상세
   - 요건 원문(title, spec\_ref, acceptance\_criteria, target\_files, priority)
   - Cursor의 dev\_note 이력
   - 그록 봇의 qa\_diff\_note 이력
   - 상태와 진행률 변경 타임라인
4. 감시 로그
   - 메시지 송수신 기록(msg\_id, type, 방향, 결과)
   - 감시 루프 오류, INI 검증 실패 기록
5. 명령 패널
   - 대상 선택: Cursor IDE 또는 그록 봇
   - 대상 항목 선택 (복수 선택 가능)
   - 명령 유형과 메모 입력
   - 전송 후 ACK 상태 표시 (대기, 수신, 완료, 실패)

**명령 유형 (발주자 UI)**

- 추가 검증 요청: 대상 항목을 IN\_REVIEW, qa\_status = PENDING으로 전환하고 qa\_diff\_note에 조건을 기록
- 수정 지시: 대상 항목을 REWORK\_REQUESTED로 전환하고 지시 내용을 qa\_diff\_note에 기록
- QA 재평가 요청: 그록 봇에 재평가 명령 전송
- 최종 승인: qa\_status = PASSED인 항목만 VERIFIED로 확정

## 7. 감시 지표 (핵심 목적)

이 시스템의 목적은 두 에이전트의 정확도를 측정하는 것이다. 아래 지표를 항목별, 에이전트별, 전체 기준으로 산출한다.

| 지표 | 정의 | 측정 대상 |
| --- | --- | --- |
| 첫 검증 합격률 | 첫 QA에서 PASSED된 항목 수 / 전체 QA 수 | Cursor 구현 품질 |
| 평균 반려 횟수 | 항목당 qa\_rework\_count의 평균 | Cursor 구현 품질 |
| 자기보고 편차 | Cursor가 보고한 progress와 QA 최종 progress의 차이 | Cursor 자기 평가 정확도 |
| 판정 일관성 | 같은 항목을 그록 봇이 재검증했을 때 판정이 일치한 비율 | 그록 봇 QA 신뢰도 |
| 결함 적중률 | 발주자가 추가 검증 요청한 항목 중 실제 결함이 확인된 비율 | 그록 봇 결함 탐지 정확도 |
| 명령 응답 시간 | 명령 전송 시각부터 ACK 수신까지 걸린 시간 | 연결 및 처리 속도 |
| 요건 충족률 | VERIFIED 항목 수 / 전체 항목 수 | 프로젝트 진척 |

**산출 규칙**

- 지표는 감시 루프가 상태 INI를 갱신할 때마다 재계산한다.
- 지표 계산에 쓰인 원본 이벤트는 이력 로그에 남겨 재계산이 가능해야 한다.

| 필드 | 쓰기 가능 주체 |
| --- | --- |
| 요건 INI 전체 | Cursor IDE (SPEC\_RESET), 발주자 (직접 편집은 금지) |
| status, progress, dev\_note | Cursor IDE (60 이하 구간에서만) |
| qa\_status, qa\_score, qa\_rework\_count, qa\_diff\_note | 그록 봇 |
| progress 80 이상, status = VERIFIED | 그록 봇 PASSED 판정 후 관제 에이전트가 확정 |
| qa\_diff\_note (추가 검증 조건) | 발주자 (UI 명령) |

**이력 로그**

- 모든 쓰기는 누가, 언제, 무엇을, 이전 값에서 어떤 값으로 바꿨는지 기록한다.
- 로그는 추가 전용이며 수정할 수 없다.
- 보관 기간은 {기간}으로 한다.

## 9. 비기능 요건

- 감시 주기: 5초 ±1초
- 처리 규모: 항목 500개, 에이전트 2개에서 UI 갱신 지연 2초 이하
- 복구: 관제 에이전트 재시작 시 마지막 정상 스냅샷과 이력에서 상태를 복원한다.
- 보안: 로컬 바인딩, 외부 전송 없음, 자격 증명 로그 기록 금지
- 호환: 요건 INI의 줄 인코딩은 UTF-8이며 BOM은 허용한다.

## 10. 수용 기준 (DoD)

1. spec.ini를 제출하면 5초 이내에 UI에 모든 항목이 표시된다.
2. 필수 키가 없는 섹션을 넣으면 거부되고 오류가 UI에 표시된다.
3. 상태 INI를 외부에서 직접 수정하면 5초 이내에 감지되어 이력에 기록된다.
4. Cursor 메시지로 progress 61 이상을 보내면 거부되고 REJECT가 반환된다.
5. 그록 봇 QA\_RESULT를 받으면 상태 INI가 갱신되고 UI에 반영된다.
6. 반려(REWORK\_REQUESTED) 시 qa\_rework\_count가 정확히 1 증가한다.
7. 같은 msg\_id를 두 번 보내도 상태가 한 번만 변경된다.
8. 에이전트 하나를 끄면 90초 안에 OFFLINE으로 표시된다.
9. 명령 전송 후 ACK 상태가 UI에 표시된다.
10. 7장 지표가 이력 로그로부터 재계산한 값과 일치한다.
11. 관제 에이전트를 재시작해도 상태가 복원된다.
12. 외부 네트워크 연결이 발생하지 않는다.
