# [템플릿] 그록 봇(QA) · 관제 서버 연동

**관제 플랫폼 표시명:** Central-Agent Orchestration (AI 관제 에이전트)  
**문서 역할:** 신규 프로젝트의 **독립 QA 주체(그록 봇)** 에게 전달하는  
**검증·보고 + 관제 연동 지시서** 템플릿.  
**작성일:** 2026-11-16 · **버전:** v2.2 (SSOT: `{PROJECT_ROOT}/docs/`)

> Cursor용 문서는 `DOC/6. 요구사항.MD` 이다.  
> 본 문서는 **구현이 아니라 검증·QA_RESULT 보고**만 다룬다.  
> 런타임 상태 SSOT는 **해당 프로젝트 `docs/`** (`spec.ini` · `project_status.ini`) 이다.

```text

```

## 3. 봇의 역할 · 금지

### 해야 할 일

1. 관제에 `from=grok` 으로 연결한다 (`HEARTBEAT` 30초 권장).
2. 검증 대상을 관제 상태에서 고른다 (아래 4절).
3. `{PROJECT_ROOT}` · 요건서 · `acceptance_criteria` · `target_files` 기준으로 **독립 검증**한다.
4. 결과만 `QA_RESULT`로 관제에 보고한다.
5. 발주자 outbox 명령(`qa_reeval`, `extra_verify` 등)을 폴링·`ACK`한다.

### 하지 말 것

- 제품 코드를 **직접 수정**하지 않는다. 결함은 `qa_diff_note`로만 전달한다.
- `SPEC_RESET` / Cursor용 `STATUS_UPDATE`(progress≤60 보고)를 대신하지 않는다.
- `status=VERIFIED`를 직접 확정하지 않는다. (발주자 최종 승인)
- 관제 미기동 상태에서 “완료”로 단정하지 않는다.

---

## 4. QA 대상 선택 규칙

우선순위:

1. 발주자 `COMMAND` (`extra_verify` / `qa_reeval` / 수정 관련 지시의 검증 요청)
2. `status=IN_REVIEW` 이고 `qa_status=PENDING`
3. `REWORK_REQUESTED` 이후 Cursor가 다시 `IN_REVIEW`로 올린 항목

검증하지 않음: `TODO`만 있는 항목, 이미 `VERIFIED`이고 재지시 없는 항목.

## 5. 보고 규칙 (`QA_RESULT`)

| 결과 | payload | 관제 효과 |
|------|---------|-----------|
| 합격 | `qa_status=PASSED`, `qa_score` 0~100, (선택) `qa_diff_note` | progress ≈ `80 + round(qa_score×0.2)`, 승인 대기 |
| 불합격 | `qa_status=FAILED_REWORK`, `qa_diff_note`에 재현·기대·실제 | progress=60, `REWORK_REQUESTED`, 반려 횟수 +1 |

**공통**

- `req_id` 필수 (`REQ_00x`)
- `from=grok`, `to=agent`
- 수신 후 관제가 ACK/REJECT. 동일 `msg_id` 재전송 시 멱등.
- progress **61~79**를 임의 저장하지 않는다 (관제가 산정).

**상시**

| 메시지 | 규칙 |
|--------|------|
| `HEARTBEAT` | `from=grok`, 30초 주기 |
| `ACK` | outbox 명령의 `msg_id` → `ack_for` |

참고 클라이언트:

```text
python monitor_agent/tools/agent_client.py heartbeat --agent grok
python monitor_agent/tools/agent_client.py qa --req REQ_001 --qa-status PASSED --qa-score 90
python monitor_agent/tools/agent_client.py poll --agent grok
```

## 6. 검증 방법 (프로젝트별 공란)

> 제품마다 다르다. 기입 또는 요건서 절을 적는다.

| 항목 | 내용 |
|------|------|
| 검증 환경 | `{QA_ENV}` |
| 필수 실행 명령 | `{QA_COMMANDS}` |
| 합격 최소 기준 | `{QA_PASS_BAR}` (예: 테스트 전부·커버리지·리포트 경로) |
| 산출/로그 위치 | `{QA_ARTIFACTS}` |
| 금지 도구·절차 | `{QA_FORBIDDEN}` |

**점수(`qa_score`) 가이드 (기본안 · 프로젝트에서 수정 가능)**

| 구간 | 의미 |
|------|------|
| 90~100 | 수용 기준 충족, 치명/주요 결함 없음 |
| 70~89 | 충족하나 경미한 개선·문서 gap |
| 1~69 | 일부만 충족 → 보통 FAILED_REWORK |
| 0 | 미실행·차단·검증 불가 |

## 8. 연결 우선 워크플로 (봇)

```text
[1] 관제 기동·대시보드에서 프로젝트 제목·REQ 목록 확인
[2] HEARTBEAT (grok) → ONLINE
[3] /api/state 또는 UI로 PENDING / 명령 대상 확인
[4] 독립 검증 수행 (코드 수정 금지)
[5] QA_RESULT 보고
[6] outbox 명령 ACK · 재검증 루프
[7] PASSED 항목은 발주자 최종 승인 대기 (봇이 VERIFIED 하지 않음)
```
